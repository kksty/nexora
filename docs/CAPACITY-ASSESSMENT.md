# 容量评估与可重复基线

日期：2026-10-26（Asia/Shanghai）。本文记录 Nexora 当前实现的有限短时容量证据、后续验收口径和容量规划方法。它不把一次小样本、合成 semaphore 调度或假模型结果推算成最大容量、生产吞吐或 SLA。相关计划见 [API 与自建模型计划](API-CONTEXT-PLAN.md)，运行指标与日志边界见 [运行诊断](DIAGNOSTICS.md)，历史验收见 [验证说明](VALIDATION.md)。

## 结论与证据边界

本轮确认的关键实现事实如下：

- 模型并发默认值 `2` 是**每个任务**的合计上限。每个任务运行时创建自己的 `Semaphore`；该任务的所有 work 共享这 2 个在飞名额。不同任务各有独立池，源码未发现跨任务共享的模型并发池。
- 名额只在模型流打开期间持有。工具执行、等待消息、后台 job 和重试退避期间不占模型名额。流结束、取消、work 进程退出都会归还或回收名额；上游无法及时关闭时，运行时停止该 work 进程后回收。
- 源码未发现全局 RPM、TPM、每日额度、费用或 token 总预算，未发现跨任务全局队列/限流，也未发现活跃 work 数量上限。默认 2 不是 RPM/TPM 限制，也不是 work 数量上限。
- 生成的 Task Compose service 未设置 CPU、内存、PID、磁盘/容器存储或 `ulimit` 限额。Web 与 Task 默认共享宿主资源；主 `compose.yaml` 也未声明这些资源限制。
- 不设置费用、步数、时长或资源耗尽的强制停止预算。模型失败会重试并显示状态；暂停、等待人工或资源不足都不能被当作任务已经完成。完成仍由现有共识、活动结算、报告与阻塞项协议判断。
- 上下文窗口要经过两层概念：客户端窗口预算与**服务端真实窗口**。Web 字段只控制适配器及压缩配置，不会自动修改 vLLM 的 `--max-model-len`、Ollama 的 `num_ctx` 或其他服务端配置。模型名、量化、显存、KV cache 设置、并发批次和最大窗口仍需在部署侧确认。
- 当前代码已把 Web 设置、环境变量、Compose service、harness adapter 和 `compaction-basic` 接到同一份启动快照；Docker 启动测试会检查模型限制进入任务 service。真实 Qwen 部署仍需确认服务端窗口、tokenizer、显存和长上下文表现，不能只凭表单或本地 fake 服务宣称生产容量。

这不是生产容量承诺。真实自建 Qwen 的吞吐、429、超时、显存与长上下文能力尚未测试。

## 三个容量维度

### 1. 单请求上下文

需要分别记录：

| 量 | 含义 | 不能混淆为 |
| --- | --- | --- |
| 服务端最大窗口 `W_server` | vLLM/Ollama 实际可接收的总 token 窗口，含输入与输出预留 | Web 中手填的窗口 |
| 客户端窗口 `W_client` | 适配器声明并用于压缩判断的窗口 | 服务端自动生效的窗口 |
| 单次输出上限 `O` | 一轮模型响应最多生成的 token | 用户输入上限或总上下文 |
| 安全余量 `M` | 为 tokenizer、工具 schema、协议封装等预留的余量 | 固定不变的服务端参数 |
| 输入预算 | 近似 `W_client - O - M`（实现还受压缩阈值约束） | 普通用户消息的字符数 |

系统提示、工具定义、历史消息、工具调用参数和工具结果都进入模型输入。思考模型可能把不可见推理 token 计入输出额度；实际计费/限流口径也由服务端决定。当前 SDK 的压缩计算以适配器声明的窗口为基础：默认阈值约为 `floor(min(W × 0.8, W - O - 65536))`，近期历史保留预算默认约为 `(W - O) × 16%`。`compaction-basic` 还会发出额外的摘要模型请求；应用将 headroom 配成安全余量时，这属于独立的实现口径，不能自行把它解释成等同于服务端的 KV cache 预留。

上下文容量未知时，本文按 **32K 总窗口、4K–8K 输出、每任务并发 1–2** 作为待实测起点。这是为了先验证协议、工具循环、压缩与显存行为，不是生产推荐。长 agent 在显存允许时可能需要更大的窗口；Ollama 官方对 agent 场景给出的能力建议也不能替代本机模型、量化和服务端配置验证。

### 2. 每任务并发与多任务 API 压力

单请求 token 成本之外，并发请求会同时增加调度队列、prefill/decode 竞争与 KV cache 占用。上下文越长，并发对显存和尾延迟的压力通常越大。服务端可能在超过内部 batch/KV 容量后排队、超时、OOM 或返回 429；具体阈值只能在实际 Qwen 服务上测。

多任务启用时，应用层理论任务许可峰值为：

```text
理论跨任务在飞峰值 = Σ(每个活动任务的 modelConcurrency)
```

这是应该施加限流的上限，不代表模型能同时高效处理这么多请求。实际共用上游额度时，还受另一个上限约束：

```text
可用在飞请求 <= min(Σ 各任务许可, 上游健康并发上限)
```

近似 RPM 与 TPM 可这样从实测均值估算；它们不是承诺，也不应使用成功请求率较高时的一次峰值外推：

```text
RPM ≈ 60 × 在飞请求数 / 平均请求秒数
TPM ≈ RPM × 每次请求输入 token 与输出 token 的平均总量
```

压缩调用也要计入请求数和 token 量；重试、思考 token、工具结果回传和缓存命中是否计入额度，要按服务端 usage 与响应头核实。没有服务端 usage 时保留未知，不用字符数伪装 token。

自建 Qwen 初测可从每任务并发 1–2 开始。单任务稳定后，再让两个任务同时发压，观察共享服务端是否出现尾延迟上升、显存下降、KV cache 驱逐、排队、429、超时或断流。只有当局部并发点重复通过，才按小步提高一个参数（活动任务数、每任务并发或窗口之一），并在每一步重新测量；不能一次同时放大三者。

### 3. 状态、会话、日志增长与进程内存

权威 `state.json` 每次变更整体序列化并通过临时文件、fsync、rename（POSIX 还同步目录）提交。发现和消息通常还重写 `task.md`/`works.md`；发现额外 durable append 到 `findings.md`。写入由任务内 mutex 串行，因此状态变大时不仅增加读盘，也可能拉长所有状态修改在队列中的等待。

任务目录还包括持续增长的 `runtime/journal.jsonl`、每 work 的 `runtime/sessions/`、harness/daemon/任务启动文本日志、证据与不可变报告版本。诊断 JSONL 默认单文件 16 MiB、总 8 份，约 128 MiB；会话、journal、证据、报告和普通文本日志不在该轮转范围内。Web 会话视图只读取每会话最多 8 MiB 尾部、400 条记录，当前没有读取更早日志的页游标；文件预览最多 512 KiB，报告草稿最多 5 MiB。另有每 work 的活动窗口上限，但不能据此推断磁盘状态长期有界。

每 work 是独立 `dsh --profile sdk` 进程和持久会话。work 数增加会带来每个 Node 进程、加载模块、工具/终端子进程、会话缓存和可能的独立 KV cache 压力；没有全局 work 上限，也没有容器资源上限。因此“四个模型请求”与“四个 work”不是同一个数：一个任务可有数十个 work，而其中最多只有 4 个同时处在本任务模型流阶段。

## 本轮短时实测

测试宿主为 Windows 11 x64、Node.js 26.9.0、AMD Ryzen 7 9700X（16 逻辑 CPU）、31.16 GiB 内存、NTFS。以下时间来自非生产、无模型、无 Docker、无网络的合成路径；主机缓存与负载会影响单个数字，不构成稳定上限或跨平台预测。

### 状态读写与 RSS

状态探针使用生产 `Engine`、发现、消息、原子状态写入和 `loadState` 路径。每次规模均做完整重载校验，发现/消息 ID、计数、共享版本、抽样哈希和序列化一致性通过。

| 发现 | 消息 | `state.json` | 保存 P95 | 读取 P95 | 批次追加 | 任务目录 | 进程 RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 50 | 0.26 MiB | 3.952 ms | 2.194 ms | 760.146 ms | 0.53 MiB | 115.137 MiB |
| 500 | 250 | 1.30 MiB | 7.693 ms | 4.538 ms | 5,121.310 ms | 2.60 MiB | 168.809 MiB |
| 2,000 | 1,000 | 5.21 MiB | 20.513 ms | 10.243 ms | 38,004.660 ms | 10.38 MiB | 181.457 MiB |

保存/读取各使用 9 个重复样本（2,000 条规模为 7 个）。2,000 条规模的中位数分别为保存 17.167 ms、读取 8.606 ms；heapUsed 为 68.872 MiB。RSS 包含探针本身与两个惰性 work，不含真实 harness 会话、模型 SDK、工具和长时间碎片趋势。

这些数字只表明该量级在那个宿主和那一次短时可完成，不能推导最多可存多少条发现、长期 RSS 斜率或最大任务目录。

### 独立任务 semaphore 与跨任务聚合

并发探针创建多个独立任务级池，每个任务同时运行多个 work，每个 work 顺序发出合成请求，并记录真实共享采样器和任务池队列。所有池并发运行，4 个任务同一时刻可实际叠加。

| 每任务许可 | 任务 | work/任务 | 请求/work | 保持时间 | 墙钟 | 单任务峰值 | 队列峰值 | 聚合峰值 | RSS |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4 | 6 | 4 | 25 ms | 747.119 ms | 1 | 5 | 4 | 54.770 MiB |
| 2 | 4 | 8 | 4 | 25 ms | 498.139 ms | 2 | 6 | 8 | 55.320 MiB |

每个任务都最终 `active=0, queued=0`，重复归还未再次释放名额，合成请求无 acquire 拒绝。聚合峰值 4/8 证明这些独立任务池允许叠加，**不证明模型或上游额度能接受 4/8 个同时请求**。现有 `tests/llm-concurrency.test.ts` 还覆盖排队、取消、迟到 acquire、进程退出回收、API/插件释放与上游流失败；本轮没有新增重复的测试。

## 真实 Qwen 与长期工况验收

以下测试需使用单独环境与实际自建 Qwen；本轮没有调用真实模型、Docker、部署或密钥。每次固定记录模型、量化、服务端版本、vLLM/Ollama 参数、GPU/显存、上下文窗口、并发配置、prompt/tool schema 版本和存储类型。

1. **协议与工具闭环**：确认 Base URL、模型路由、鉴权、流式内容、工具调用参数分片、工具结果回传和最终回答都可完成。模型列表成功或一次短对话成功不证明这些能力。
2. **单请求窗口**：先用 32K 窗口、4K–8K 输出、每任务并发 1，测普通/长输入、思考 token、压缩前后以及工具循环。验证服务端真实收到并支持声明窗口；对 Ollama，用 `ollama ps` 核实 `CONTEXT`、CPU offload，并确认 `num_ctx` 不是 Web 自动修改。对 vLLM，确认 `--max-model-len`、模型原生窗口和显存参数一致。
3. **单任务并发**：每任务从 1 升到 2，分别测短上下文与接近压缩阈值的请求。记录排队时间、首块、首文本、流时、P50/P95/P99、超时、429、断流、压缩次数、usage 和显存曲线。
4. **多任务合计压力**：由 2 个任务各自并发 1 开始，再按一个变量小步增加。每个时刻同时记录每任务与全服务的在飞请求、队列、RPM/TPM 和响应错误，验证理论总和与上游健康上限。
5. **长 agent soak**：至少覆盖多任务长时间运行、反复工具调用、接近窗口、多次压缩、重试和取消。持续记录 daemon/work RSS、会话与 journal、`state.json`、`findings.md`、任务目录、磁盘余量、状态写入 P95、恢复耗时和事件循环延迟；同时观察上游显存、KV cache 和缓存命中。
6. **故障恢复**：断言并验证服务端重启、模型流中断、空闲超时、上游清理失败、任务/容器重启、429 退避和取消不会泄漏名额或把等待/失败标为完成。恢复后检查持久会话、活动核对和压缩后继续工具循环。
7. **日志可读性**：分别验证会话 8 MiB 尾读、journal、证据和报告版本增长。记录诊断轮转是否正常，以及超过当前查看窗口后需要归档还是分页。

至少以 1 小时短 soak 建立趋势，再以数小时工况确认。若短测已显示 RSS、状态写入或目录增长没有趋于稳定，不应直接进入更长时间 soak 来“等它恢复”，应先定位。

## 需持续观测与规划阈值

| 记录项 | 用途 | 触发复核的条件 |
| --- | --- | --- |
| 每任务/全局在飞、队列长度、P95/P99 | 区分应用调度排队与模型变慢 | 队列长期非空、P95 连续上升、多任务加总超过声明上限 |
| 429、超时、断流、重试、finish reason | 判断上游压力与错误分类 | 任意持续 429、重试占比上升、超时集中到长上下文 |
| 输入/输出/推理/缓存 token 与 usage 来源 | 算 RPM/TPM 和上下文成本 | 只有字符数、字段缺失，或压缩/思考 token 未覆盖 |
| 压缩触发、耗时、额外请求、压缩后成功 | 判断压缩带来的 API 与质量风险 | 频繁压缩、摘要失败、压缩后工具循环退化 |
| 会话、journal、证据、报告、`state.json`、任务目录 | 预计磁盘增长与恢复成本 | 达到预留容量比例、清理失败、增长无界 |
| daemon 与 work PID/RSS、CPU、线程、事件循环延迟 | 判断进程规模与资源竞争 | RSS 长期斜率、进程数增长、事件循环 P99 上升 |
| 服务端显存、KV cache、offload、batch 与窗口 | 判断模型侧承载和陈旧服务端配置 | offload 增加、KV cache 驱逐、OOM、实际小于声明窗口 |

不设置与业务无关的固定“超过就失败”预算。P95、磁盘占用和并发阈值应作为容量门禁与人工规划触发器，由部署方按硬件和任务重要性确认；任务本身不因耗时、步数、费用或资源耗尽自动完成。

## P0/P1/P2 与触发条件

### P0：上线或多任务启用前

- **P0 服务端窗口确认**：真实 Qwen 的模型、量化、显存、服务端最大窗口、输出预留和压缩后可用上下文已实测。32K+4K–8K 只是待测起点，Web 字段不会扩大服务端容量，也不是生产推荐。
- **P0 协议与工具循环**：实际服务端完成流式工具调用与结果回传。开放兼容接口或“模型列表可读”不足以放行。
- **P0 上下文设置接线**：源码和 Docker service 测试已确认从 Web 保存、环境变量、Compose service、harness 适配器到 `compaction-basic` 的上下文窗口、输出、安全余量与压缩比例使用同一份启动快照；仍需在真实 Qwen 上验证服务端是否接受声明窗口。
- **P0 至少一次真实总压力验证**：若会同时运行多个任务，必须测得共享上游健康并发与任务池相加后的表现；若使用固定 RPM/TPM 共用额度，需有跨任务协调/全局节流，或明确只允许安全数量任务及人工排队。只有在提供方有固定额度且多任务会共享时才成为逻辑必要性，不能凭空设置。
- **P0 长上下文稳定性**：接近声明窗口前发生压缩，压缩后工具循环、会话恢复与 usage 仍可信；服务端没有超出 KV cache/显存后静默降级或挂死。

### P1：稳定性与容量运营

- 多任务总和导致 429、超时、断流、排队持续增加，或单任务/全局健康并发被突破。
- 状态写入 P95、读取/恢复耗时或任务目录增长超过部署方预留的运行包络；状态 mutex 排队影响正常操作。
- work 进程数或 RSS 使宿主内存、PID、文件句柄、磁盘余量或事件循环进入危险区。当前没有固定 work/资源上限，触发时应先做接纳控制或分宿主，仍不能把资源不足写成任务完成。
- journal、会话、证据或普通日志无法读取/备份/恢复，或诊断轮转之外的文件长期增长缺少运营方案。
- 模型或服务端重启、取消、429 退避、上游清理失败后出现名额泄漏、重复执行、错误完成或活动阻塞不收敛。

### P2：长期存储与可维护性
